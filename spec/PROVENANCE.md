# Provenance of the CipherSift specification

This file records where the content of `spec/`, `rules/` and `spec/conformance/` comes
from, and the clean-room process under which CipherSift is implemented.

## Clean-room process

1. **Specification author** (this delivery). Had read access to the sources listed under
   "Inputs" below, wrote the specification, the rule converter, the conformance cases and
   the tools in `spec/tools/`. No source code or code comment of any existing scanner was
   copied into, or translated for, these deliverables; algorithms are described in prose
   and tables in the author's own words. The only material carried over verbatim is listed
   under "Carried over" and is BF-CBOM's own work.
2. **Implementer**. Receives only:
   * `spec/` (this file, `SPEC.md`, `rule-schema.json`, `conformance/`, `tools/`),
   * `rules/`,
   * `LICENSE`.

   The implementer MUST NOT read the reference tool (the Crypsy fork described below), the
   upstream Crypsy/Crypistry sources, or the BF-CBOM benchmark corpora and results. Questions
   go to the specification author, whose answers are added to `SPEC.md`.
3. **Acceptance**. The implementation passes the conformance suite (`spec/conformance/`)
   and the tests required in SPEC.md section 16.

The BF-CBOM benchmark material (`corpus/`, `corpus-native/`, `results/`) was not read or
used for any part of this delivery.

## Written new for CipherSift

* `spec/SPEC.md`, `spec/rule-schema.json`, this file, `spec/conformance/README.md`,
  `spec/conformance/deviations.yaml`.
* The rule format (keys, anchors, conditions, schema) — not the Crypistry schema. Several
  pattern *concepts* exist in the upstream format under other names and were renamed by the
  converter: `call` (upstream `call`), `firstString` (`args_matches_regex`), `stringContains`
  (`args_contains_string`), `assign` (`field_assign`), `valueContains` (`value_contains`). The
  rule-id taxonomy (`<lang>.<category>.<family>[.<variant>]`, e.g. `rand.prng.insecure`,
  `cert.validation.disabled`), some asset subtypes (`rc4-cipher`, `null-cipher`,
  `prng-insecure`, `cert-validation-disabled`, `hostname-verification-disabled`,
  `jwt-none-algorithm`, `pkcs1-v1_5-encrypt`, `x509`) and the rule-name pattern
  "`<X> usage in <Language>`" follow the conventions of the upstream Go/Ruby rules, on which
  the fork modelled its Java/Python rules. These are functional names and conventions; no
  upstream rule text, description or anchor list is carried over.
* `rules/dependencies/dep.maven.yaml` (45 Maven coordinate patterns) and the 41 PyPI
  packages added from `spec/tools/pypi-extra.yaml`, written from public project
  documentation.
* Conformance cases other than the two `fork-fixtures` cases (21 cases), their inputs and
  the hand-written Maven expectations.
* Tools: `convert_rules.py` (rule conversion), `check_rules.py` (schema + semantic
  validation), `regex_parity.py` + `RegexParity.java` (Python/Java regex equivalence over
  all rule regexes), `make_expected.py` (expected-findings generation from the reference
  tool), `conformance.py` (CBOM normaliser and comparator).

## Reproducing the generated files

```sh
FORK=<BF-CBOM Crypsy fork checkout>            # rule source (contains crypistry/)
BUNDLE=<reference tool bundle>                 # runnable install with venv/ and crypistry/
python3 spec/tools/convert_rules.py --registry $FORK/crypistry --out rules
$BUNDLE/venv/bin/python -I spec/tools/check_rules.py rules
JAVA=/usr/lib/jvm/jdk-25.0.1/bin/java $BUNDLE/venv/bin/python -I spec/tools/regex_parity.py rules
$BUNDLE/venv/bin/python -I spec/tools/make_expected.py --registry $BUNDLE/crypistry --rules rules \
    --cases spec/conformance/cases --deviations spec/conformance/deviations.yaml
```

(`check_rules.py` needs PyYAML and jsonschema; `regex_parity.py` needs PyYAML and a JDK.)
